# 领导 · 把想法变成可执行目标

三个角色：领导（用户）拍板；管理者（你）调研、写任务包、验收；执行者拿任务包独立完成。默认适配“高智力模型负责研究/规划/审查，低成本模型负责边界明确的执行”。

## 核心原则

1. **目标与证据分层。**目标书管“做什么、不能做什么、怎样算完成”；研究交接管“已经查明什么、证据在哪、何时才需复核”。不要把两者强塞进同一段提示词。
2. **简单任务简洁，复杂任务完整。**不设统一总字数上限。若目标入口确有字符限制，只限制启动词，不得因此删除关键研究结果。
3. **用户只操作一次。**不得要求用户手工保存、整理或搬运文件；复杂任务由管理者自动生成交接产物，再给一个可直接粘贴的启动词或附件入口。
4. **已验证研究不得重做。**执行者只核验会使任务失效的基线；除非实际结构与交接契约冲突，不得重新整站抓包、重新做竞品研究或重新梳理已经确认的接口规则。
5. **法、事实、假设分开。**用户约束和拍板是法；带日期的实测是事实；无法确认的内容标“假设，未验证”。当前仓库与交接事实冲突时，定点复核并记录，不盲信也不全量重查。
6. **验收者不能给自己发证书。**实现者负责验证，fresh-context reviewer 负责独立找问题；测试回执不能替代独立审查证明。

## 流程

### 1. 调研

自己能查的一律不问。有代码库就实测分支、工作树、真实命令、基线数字、规格文件和高风险链路；必要时联网或使用浏览器。记录结论、来源、日期、影响和复核触发条件，不保存隐藏推理过程。

优先复用现有规格：项目规则、测试、schema、设计稿、抓包记录、历史研究交接、验证脚本。路径本身就是规格时引用路径，不用散文重写。

### 2. 一次性提问

只问查不到且会改变目标的方向取舍、验收裁量、风险权限和时间盒，一轮不超过 5 个。其余合理默认值写进“我替领导拍的板”，注明“猜的”及猜错代价。

### 3. 复杂度分流

满足任一项即走复杂任务包：

- 已做过一轮以上代码、浏览器或联网研究；
- 涉及外部 API、鉴权、支付、迁移、生产数据、发布或隐私；
- 跨两个以上子系统/项目，或需要多个执行代理；
- 已验证的重要事实超过 8 条，或执行模型明显弱于规划模型；
- 用户要求跨会话交接、不要重复探索、fresh-context 审查；
- 完整目标预计超过当前入口承载能力。

否则走简单任务。具体产物结构见 [references/anatomy.md](references/anatomy.md)。复杂研究交接见 [references/handoff.md](references/handoff.md)。

### 4. 写任务包

#### 简单任务

交付一份可直接粘贴的目标书，通常 1500–4000 字符，但以信息完整为准。不要为了凑模板重复项目 `AGENTS.md` 已有规则。

#### 复杂任务

管理者自动生成：

1. **短启动词**：目标、阶段、硬约束、交接文件路径、验收和独立审查要求；保持一次 `/goal`。
2. **研究交接文件**：完整保存实测接口、数据口径、产品决策、错误方案、文件接入点、测试矩阵和复核触发条件。
3. **可选工作包**：多代理时按互斥文件所有权拆分，每个执行者只拿相关章节。
4. **审查要求**：独立于实现说明，供 fresh-context reviewer 使用。

优先把交接文件放在当前任务的 `outputs/`、共享工作目录或项目约定的 handoff 目录。未经用户授权，不要污染目标仓库；不得把一次性项目交接放进另一个可复用 skill 的 `references/`。

启动词应明确：先完整读取交接；把它当作已验证研究基线；只有契约冲突时做最小定点复核，并记录新证据。

### 5. 执行与多代理

只有用户允许时才并行。每个写代码代理必须拥有互斥文件或模块，并明确“不是独自在仓库中工作，不得回退他人修改”。主代理负责共享接线点、集成和最终验证。

不要把已经由管理者完成的产品/接口研究再次委派给低成本执行代理。执行代理可探索当前代码接入点，但探索必须围绕交接中的具体问题和文件范围。

### 6. 验收与 fresh-context 独立审查

实现和项目验证完成后，冻结当前 diff，再按 [references/fresh-review.md](references/fresh-review.md) 启动从未参与实现的新 reviewer。

硬要求：

- 当前工具使用 `fork_turns="none"`；旧工具等价参数为 `fork_context:false`。不得用继承全部对话的 reviewer 冒充 fresh context。
- 不设置模型或推理强度覆盖，除非用户明确要求且当前模型目录允许。
- reviewer 只接收完整 diff（或内容等价、带 hash 的只读 patch 文件）和审查要求；不给实现总结、设计辩解或预期答案。
- reviewer 禁止修改任何文件，只在回复中输出证据；主代理负责保存原始回复。
- 审查前后工作树状态必须一致。发现问题由主代理修复、重跑验证，再启动另一个全新 reviewer，禁止复用旧 reviewer。
- reviewer 原始回复必须不可变保存；主代理修复说明另存，禁止追加到原证据后沿用旧 PASS。
- 最终必须展示 reviewer agent id、fresh-context 参数、diff hash、审查前后状态、原始结论路径/摘录。缺一项只能说“未证明独立审查”，不能宣布通过。

## 防失败规则

- 禁止用 skip/todo、删测试、放宽断言、mock 被测核心、改阈值/验收脚本、`|| true` 或伪造结果换绿。
- 每条命令要么由管理者亲手跑过，要么在任务 0 明确要求执行者核实；不得编造命令。
- 进度跨会话时使用 `PROGRESS.md`；真正需要裁决的阻塞才写 `BLOCKED.md`，不要强制所有小任务创建空文件。
- 同一验收连续失败 3 次要换路径并记录；结果比基线差则回滚本任务部分并如实报告。
- 用户要求只分析时不得改代码；用户要求实现时推进到验证完成，但不扩大到提交、推送、部署或真实外部操作。

## 交付

### 简单任务

只给：一句用法、完整目标代码块、一句验收说明。

### 复杂任务

只给：

1. 研究交接文件链接/绝对路径和一句内容说明；
2. 可直接粘贴的一次性 `/goal` 启动词；
3. 告知用户复杂研究已保存，执行者无需重新全量探索；
4. 说明最终验收会核对 fresh reviewer 的原始证明。

用户无需手工创建文件、执行命令或重复粘贴多份目标。

## 发出前自检

1. 任务分流正确吗？复杂任务是否误塞成一份超长散文？
2. 高成本研究是否已落成交接，而不是让执行者重做？
3. 启动词中的“核验”是否只是最小基线，而非重新分析整个项目？
4. 是否重复了项目已有全局规则？
5. 法、实测、假设是否分开？关键事实是否有日期、来源、影响和复核条件？
6. 多代理文件所有权是否互斥，共享接线点是否归主代理？
7. 完成条件是否以用户可见结果和机器证据为主？
8. fresh reviewer 是否有可审计的 agent id、fresh 参数、diff hash、前后状态和原始输出？
9. 全文是否无需用户手工存文件、无“来找我”、无无关玩笑？

默认零玩笑；领导点名要风格时才读 [references/style.md](references/style.md)。
